# 지도 · 위치 기능 기획 노트

> 아직 **구현 전** 문서입니다. 아이디어와 조사 결과를 모아두고 나중에 같이 검토하기 위한 메모예요.
> 결정된 것은 ✅, 아직 정할 것은 ❓ 로 표시했습니다.

카드에 **장소**를 붙이고, 그걸 **지도에 핀으로** 보여주는 기능.
"가고 싶다고 저장해둔 곳"과 "실제로 다녀온 곳"이 지도 위에 쌓이는 그림입니다.

---

## 1. 위치 데이터가 들어오는 4가지 경로

정확도 높은 순서입니다. 네 가지 모두 결국 **"장소 이름 → 네이버 지역검색 → 후보 중 확정 → 좌표 저장"** 이라는
같은 파이프라인으로 흘러들어가므로, **D를 먼저 만들면 A·B·C는 그 위에 얹는 얇은 껍데기**가 됩니다.

> **적용 후 정정 (실사용 피드백)**: 실제로 써 보니 **인스타 위치 태그(A)가 대충 찍힌 경우가 많았습니다.**
> 동네·건물 이름만 달려 있거나 실제 간 가게와 다른 곳이 붙어 있어서, **B(캡션에서 AI가 추출)를 먼저 쓰고
> A는 B가 실패했을 때의 폴백**으로 순서를 뒤집었습니다. 캡션 뭉치에서도 위치 태그를
> `게시물 위치 태그(부정확할 수 있음)`으로 표시해 AI가 캡션 본문을 우선하도록 했습니다.

### A. 인스타그램 위치 태그 (이미 받아오고 있음) — 폴백으로 강등

Apify가 게시물에서 `locationName` 을 같이 주고 있는데, 지금은 이걸 캡션 뭉치에
`장소: ○○` 형태로 섞어서 AI에 넘기고 있습니다 (`supabase/functions/analyze-link/index.ts`).
이걸 **별도 필드로 분리**하면 바로 쓸 수 있습니다.

- 장점: 게시자가 직접 찍은 태그라 정확도 최상
- 한계: 위치 태그가 없는 게시물이 많고, `locationId` 는 네이버와 연결되지 않음 (이름만 씀)

### B. 캡션에서 AI가 추출 ✅ 1순위

`analyze-link` 의 프롬프트에 `place_query` 필드 하나를 추가해서
"속초 중앙시장 물회" 같은 **검색어**를 뽑게 합니다.

- 장점: 프롬프트 몇 줄 추가 수준, 비용 거의 그대로
- 한계: **이름 문자열일 뿐 좌표가 아님** → 반드시 지역검색을 한 번 더 거쳐야 함
- 주의: AI 추측이므로 틀릴 수 있음 → `source: 'AI'` 로 표시하고 카드에 "확인 필요 ⚠️" 배지

### C. 네이버 지도 링크 붙여넣기

`naver.me/xxxx` 또는 `map.naver.com/p/entry/place/12345678` 링크를 복사하면
지금 인스타 링크 감지하는 것과 **똑같이 하단 배너가 뜨고** 카드가 만들어지는 흐름.

- 장점: 사람이 이미 "이 가게"라고 특정한 링크 → 가장 정확
- 구현: Edge Function에서 단축링크 리다이렉트를 따라가 → 페이지의 og 태그에서 가게 이름 추출 → 지역검색으로 좌표 보정
- ⚠️ **가장 불확실한 경로**: 네이버 place id로 직접 조회하는 공개 API가 없고,
  인스타처럼 네이버가 서버 요청을 막을 가능성이 있음 → 실패하면 D로 폴백

### D. 직접 검색해서 고르기 ✅ 여기부터 시작하기로 결정

카드 폼에 `📍 장소` 칸을 두고, 가게 이름을 치면 네이버 지역검색 결과가 뜨고 하나를 탭해서 확정.

- AI가 틀렸을 때의 **수정 수단**
- 링크 없이 만든 카드("친구가 추천한 데")의 **유일한 입력 수단**
- → 사실상 필수 기능이라 1순위

## 2. 데이터 모델 ✅ 배열로 가기로 결정

한 카드에 여러 장소가 들어가는 경우가 이미 있습니다 (예: "을지로 노포 맛집 투어").
나중에 마이그레이션을 다시 하느니 처음부터 배열로 둡니다.

```jsonc
places: [
  {
    "name": "속초 중앙시장",           // 표시용 이름
    "address": "강원 속초시 중앙로147번길 12",   // 도로명 우선, 없으면 지번
    "lat": 38.2070,                  // WGS84 위도 (없을 수 있음)
    "lng": 128.5918,                 // WGS84 경도 (없을 수 있음)
    "category": "관광,명소>시장",       // 네이버가 주는 분류 (선택)
    "url": "",                       // 네이버 지도 링크 (선택)
    "source": "MANUAL"               // INSTAGRAM | AI | NAVER_LINK | MANUAL
  }
]
```

설계 포인트:

- **좌표 없는 장소도 저장 가능**하게 (`lat`/`lng` null) — 이름만 아는 상태도 카드엔 표시, 지도에만 안 뜸
- `source` 를 남겨두면 **AI 추측 장소만 골라 "확인 필요" 배지**를 달 수 있음
- UI는 당분간 **첫 번째 장소 1개 기준**으로 만들고, 데이터 구조만 열어둠
- localStorage 모드도 그대로 호환 (그냥 배열 필드 하나 늘어나는 것)

### Supabase 변경 사항 ⚠️ 잊지 말 것

`supabase/schema.sql` 에 컬럼을 추가하고, **대시보드 → SQL Editor** 에서 아래를 한 번 실행해야 합니다.
기존 데이터는 그대로 두고 빈 배열로 채워지므로 안전합니다.

```sql
alter table public.contents
  add column if not exists places jsonb not null default '[]'::jsonb;
```

- 기존 카드는 자동으로 `[]` 가 되어 아무 영향 없음
- 이 마이그레이션 **전에 새 코드가 배포되면** 저장 시 "column places does not exist" 에러가 납니다
  → **SQL 먼저 실행 → 그다음 머지** 순서를 지킬 것
- `schema.sql` 은 여러 번 실행해도 안전하게 쓰여 있으므로, 전체를 다시 Run 해도 됩니다
- 지도에서 영역으로 검색하는 기능까지 가면 인덱스를 고민 (당장은 카드 수가 적어 불필요)

## 3. 지도 화면 UI ✅ 탭 안 리스트↔지도 토글로 결정

탭 구조는 지금처럼 `🗓️ 할 것들 / ✅ 한 것들` 두 개를 유지하고,
각 탭 안에서 `📋 목록 / 🗺️ 지도` 를 토글합니다.

```
[ 🗓️ 할 것들 4 ][ ✅ 한 것들 2 ]          ← 기존 탭
[ 전체 · 맛집 · 여행 … ]      [📋|🗺️]    ← 태그 필터 + 보기 토글
─────────────────────────────────────
            (목록 또는 지도)
```

좋은 점: **기존 필터가 지도에도 그대로 적용**됩니다.

- 할 것들 탭 → 태그 필터가 지도 핀에도 적용 (`맛집` 만 지도에 보기)
- 한 것들 탭 → 달력에서 고른 날짜가 지도에도 적용 (그날 동선만 보기)

핀 디자인:

- 할 것 = 앰버색 빈 핀 (아직 안 간 곳)
- 한 것 = 로즈색 채운 핀 (다녀온 곳)
- 좌표 없는 카드는 지도에 안 뜨므로, 지도 화면 하단에 "위치 미등록 3개" 같은 안내 + 탭하면 목록

> 참고: 처음 검토했던 **"지도 전용 탭 3번째"** 안은 할 것/한 것을 한 화면에 겹쳐 볼 수 있다는 장점이 있었습니다.
> 토글 방식으로 만들어보고 아쉬우면 지도 화면 안에 "할 것도 같이 보기" 체크박스를 추가하는 걸로 흡수 가능.

## 4. 지도 위에 얹을 아이디어 (우선순위 순)

### 4-1. 📍 내 주변 — 개인적으로 가장 기대되는 기능

현재 위치에서 가까운 **'할 것'** 순으로 정렬해서 보여주기.

> 데이트하러 나가서 *"여기 근처에 우리가 가고 싶다고 저장해둔 데 있나?"*

이 앱에서 저장한 것들이 실제로 **다시 꺼내지는** 순간을 만들어주는 기능입니다.
지도보다 이게 더 자주 쓰일 수도 있어요. 브라우저 위치 권한만 있으면 되고 외부 API도 필요 없습니다
(좌표만 있으면 거리 계산은 직접 가능).

### 4-2. 핀 탭 → 미니 카드

핀을 누르면 말풍선으로 사진 썸네일 + 제목 + 날짜, 탭하면 원래 카드로 이동.

### 4-3. 완료 핀 = 사진 썸네일 마커

다녀온 곳은 그날 찍은 사진을 동그란 마커로. 지도가 곧 **"우리 발자국"** 이 됩니다.
핀이 많아지면 클러스터링 필요.

### 4-4. 연말 결산 / 커버리지

- "올해 우리가 찍은 지도" — 완료 핀만 모아서 한 장
- "서울 25개 구 중 9개 정복" 같은 진행도 (주소 문자열에서 구/시 추출하면 API 없이 가능)

### 4-5. 데이트 코스 그리기

같은 날짜의 완료 핀들을 선으로 이어서 그날 동선 표시. 달력 기능과 자연스럽게 붙습니다.
(길찾기 API 없이 직선으로 이어도 충분히 예쁨)

### 4-6. 지도에서 바로 카드 만들기

지도를 길게 눌러 그 자리에 카드 추가. 역지오코딩으로 주소를 채워줌.

### 4-7. 그 밖에

- 지역별 그룹핑 (서울/경기/강원…), 동네·지하철역 기준 묶기
- "이 동네 가면 들를 곳" — 지도 영역 안의 할 것들만 필터
- 완료 핀에 별점/재방문 의사 표시

## 5. 필요한 API 조사 결과

> ⚠️ 조사 시점에 ncloud.com, ncloud-docs, developers.naver.com, developers.kakao.com 등
> **공식 문서 도메인이 작업 환경에서 차단**되어 있어, 검색 결과 스니펫과 기술 블로그에서 모은 정보입니다.
> **가입 직전에 공식 페이지에서 반드시 재확인할 것.**

### 네이버 API는 성격이 다른 두 개입니다

| | **네이버 검색 API (지역)** | **네이버 지도 API (Maps)** |
|---|---|---|
| 가입처 | NCP → **NAVER API HUB** | NCP → **Maps** |
| 용도 | 가게 이름 → 주소·좌표·카테고리 | 지도 화면 렌더링 |
| 키 | Client ID + Secret (**비밀**) | Client ID (**브라우저 노출 전제**) |
| 무료 | **0~775,000건 0원 / 일 최대 25,000건** ✅ 요금표 확인 | 월 1,000만 건 (Web Dynamic Map) |
| 우리 예상 사용량 | 하루 수십 건 | 하루 수십 건 |

> **정정**: 처음에는 검색 API를 "네이버 개발자센터에서 카드 없이 발급"이라고 적었는데 **틀렸습니다.**
> 검색 API는 **NCP의 NAVER API HUB로 이관**되어, 개발자센터의 애플리케이션 등록 화면에는
> 로그인·인증서·카페·캘린더·캡차만 남아 있습니다. 실제 등록은 NCP 콘솔에서 합니다.

- **검색 API**: NCP 콘솔 → NAVER API HUB → Application 등록 → `지역`(NAVER Search Local API) 선택.
  요금표에서 **0~775,000건 0원 / 일 최대 25,000건** 확인 (2026-08 기준)
  - "한시적 무료 제공 정책은 추후 변경될 수 있습니다"라는 단서는 검색어 트렌드·쇼핑 인사이트의
    **유료 구간**에 붙은 것이고, 검색 API 자체는 무료 구간으로 잡혀 있음
- **지도 API**: 무료 한도는 크지만 **결제수단 등록을 요구**한다는 서술이 여러 곳에 있음
  - 2023년 1월부터 **"대표 계정 1개"에만 무료** (개인은 휴대폰 번호 기준 1계정)
  - Application 등록 후 **서비스 URL 등록 필요** → `jjazzking.github.io`
  - 조사 중 *"AI NAVER API ▶ 지도 API 신규 이용 신청 차단"* 공지가 보였는데,
    구버전을 닫고 신규 Maps로 유도하는 내용으로 보임 — 가입 화면에서 확인 필요

### 호출 규격 (개발 가이드 확인 완료) ✅

```
GET https://naverapihub.apigw.ntruss.com/search/v1/local?query=…&display=5
헤더: X-NCP-APIGW-API-KEY-ID  (Client ID)
      X-NCP-APIGW-API-KEY     (Client Secret)
```

- 검색 API는 **GET**. `Content-Type`은 POST 방식(검색어 트렌드·쇼핑 인사이트)에서만 사용
- 하루 호출 한도 25,000회

확인된 실패 (참고용):

- `naveropenapi.apigw.ntruss.com/v1/search/local.json` → **404 `URL not found`**
  (게이트웨이가 응답 = 호스트는 유효하나 경로 없음). 구 AI NAVER API 주소라 쓰면 안 됨

실패하면 응답 코드·본문 일부가 **카드 폼 화면에 그대로 표시**된다
(Edge Function 로그에도 `place-search:` 로 남는다).

### 구현할 때 쓸 구체적인 사실들

- 지역검색 응답의 **`mapx`, `mapy` 는 10,000,000 으로 나누면 WGS84 경도/위도**
  (예: `1270575397` → `127.0575397`) — 걱정했던 구형 좌표계 변환 불필요 ✅
- 응답 필드: `title`(가게명, **`<b>` 태그가 섞여 나와 제거 필요**), `category`, `address`(지번),
  `roadAddress`(도로명), `link`(업체 홈페이지 — **네이버 플레이스 링크가 아님**), `mapx`, `mapy`
- 한 번에 받는 결과 개수가 적음(5개 내외로 기억) → 후보 목록은 그 안에서 고르는 UI로

### 키를 어디에 두는가

| 키 | 성격 | 저장 위치 |
|---|---|---|
| `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET` (검색) | **비밀** | **Supabase 시크릿** (Anthropic 키와 같은 자리) |
| 지도 JS API Client ID | 브라우저 노출 전제, 도메인 제한으로 보호 | GitHub Actions 시크릿 → 빌드에 주입 |

→ 검색·지오코딩은 브라우저에서 직접 부르면 키가 노출되고 CORS도 막히므로,
`analyze-link` 옆에 **`place-search` Edge Function을 하나 더** 만듭니다. 기존 구조 재활용.

### 지도 렌더링 대안 (카드 등록이 부담스러우면)

좌표를 우리 DB에 갖고 있으므로 **지도만 갈아끼우는 건 어렵지 않습니다.**

| | 카드/계정 | 국내 상세도 | 비고 |
|---|---|---|---|
| 네이버 지도 | NCP 가입 + 카드 | 최상 | 기본안 |
| 카카오맵 | 카카오 계정, 2026-07-21부터 무료 쿼터 방식 변경, 초과 시 비즈월렛 | 최상 | 사정이 네이버와 비슷 |
| **Leaflet + OpenStreetMap** | **아무것도 불필요** | 보통 | 핀 찍기 용도로는 충분 |
| VWorld (국토부) | 키 발급 필요, 무료 | 좋음 | 국내 데이터 기반 |

## 6. 단계별 로드맵

각 단계가 그 자체로 쓸모 있게 끊었습니다.

| 단계 | 내용 | 새 외부 의존성 | 상태 |
|---|---|---|---|
| **1** | `places` 필드 + 폼의 📍 장소 검색·선택 + 카드에 장소 표시 | 네이버 검색 API | ✅ **구현 완료** |
| **2** | 리스트↔지도 토글, 핀 찍기·색 구분, 핀 탭 → 카드 | Leaflet + OpenStreetMap (계정 불필요) | ✅ **구현 완료** |
| **3** | 인스타 위치 태그 분리 + AI 캡션 장소 추출 → 자동 채움 | 없음 (기존 함수 확장) | ✅ **구현 완료** |
| **4** | 네이버 지도 링크 붙여넣기 → 카드 생성 | 없음 | |
| **5** | 내 주변 / 코스 / 결산 등 재미 기능 | 없음 | |

1·2단계까지면 "우리 지도"가 완성되고, 3·4는 손을 덜어주는 자동화, 5는 재미 요소입니다.

## 7. 아직 정하지 않은 것 ❓

- ~~지도 렌더링을 네이버(카드 등록)로 갈지, Leaflet(무료)으로 시작할지~~
  → ✅ **Leaflet + OpenStreetMap으로 시작**. "지도 API는 차순위"라는 결정에 맞춰
  계정·결제수단 없이 바로 쓸 수 있는 쪽을 골랐다. 좌표는 이미 우리 DB에 WGS84로
  들어 있으므로, 나중에 네이버로 바꿀 때 손댈 곳은 `ContentMap.jsx` 상단의
  `TILE_URL` / `TILE_ATTRIBUTION` 과 지도 생성부뿐이다.
  - 남은 아쉬움: OSM은 국내 **가게 단위 라벨이 약하다**. 핀 위치는 정확하지만
    배경 지도에 상호가 잘 안 뜬다 → 쓰다가 답답하면 그때 네이버로 교체 검토
- 한 카드에 장소가 여러 개일 때 **UI를 언제 확장할지**
  (카드·폼은 전부 보여주고, 지도는 장소마다 핀을 따로 찍는다)
- 지도에 **할 것 + 한 것을 겹쳐 보는 옵션**을 넣을지
- 위치 정보가 공개 사이트에 그대로 노출되는 점 — 집 근처 같은 건 저장하지 않기로 할지
  (지금도 링크를 아는 사람은 보드를 다 볼 수 있는 구조)
